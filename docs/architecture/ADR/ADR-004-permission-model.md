# ADR-004: 权限模型与乐观锁防覆盖边界 (Permission & Optimistic Locking)

- **状态**: Accepted
- **日期**: 2026-09-03
- **决策者**: 用户 & Sol (GPT-5.6 Sol High)

## 背景与问题
用户在日常工作中会同时打开 Obsidian 客户端与个人工作台。如果两处同时编辑同一个笔记，容易发生严重的并发竞争：“后保存覆盖前保存”，导致用户在某一侧编辑的内容被无感知地冲掉。
同时，用户 Vault 中存在 `.obsidian` 配置目录、`credentials` 敏感凭证，以及包含实际 API 密钥的工程笔记。

## 决策内容
1. **基于 SHA256 内容快照的乐观锁 (Optimistic Locking)**：
   - 每次读取笔记时，API 返回经过单次磁盘读取得到的 authoritative SHA-256 hash（`current_hash`）；
   - 客户端在保存时，请求体必须携带 `expected_hash`；
   - 服务端在同一个 per-path lock 临界区内，先比对当前磁盘文件的最新 sha256。若不匹配，坚决拒绝写入并返回 `409 Conflict`（"文件已被外部修改，请重新加载"），界面弹出告警引导用户重新拉取最新版本；
2. **原子文件写入 (Atomic Write)**：
   - 使用同目录临时文件写入、`flush()`、`fsync()`，最后通过 `os.replace` 原子替换原文件，杜绝服务崩溃造成的半拉文件损坏；
   - 新建笔记时使用底层文件系统的 `open(path, "x")`（O_EXCL 原子互斥），若目标文件已存在立即 409 拦截，绝不静默覆盖；
3. **敏感信息与排除区硬隔离 (Secret Isolation)**：
   - 扫描器首层拦截：`.obsidian`、`.claudian`、`credentials` 等系统及凭证目录全量跳过；
   - 正则引擎实时检测：匹配常见高熵密钥模式（如 `sk-...`、`AKIA...`、`KEY=...`），命中即跳过入库，记录为 `secret_skipped` 审计日志；
   - 读取安全二次拦截：`/api/file/content` 读取时再次对同一字节快照重跑检测器，双保险杜绝敏感密钥泄露到前端界面。

## 收益与代价
- **收益**：在不需要分布式锁或重量级消息队列的前提下，以极轻量优雅的方式完美解决了本地双写覆盖问题，确保了用户核心知识资产的绝对安全性。
