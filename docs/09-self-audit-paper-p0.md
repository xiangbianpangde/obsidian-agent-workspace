---

## 为什么自审查需要不同的纪律

Sol 两次抓到我的盲区：把「测试通过」当成「验证有效」，把「写完了」当成「做对了」。
因此本轮自审查的核心动作是：**先区分「我声称的」与「我证明过的」，再攻击后者**。

## 二、发现的两个真实缺陷

### 缺陷 1：恢复会静默丢弃确实存在的笔记

**攻击方式**：让 intent 记录的前缀与实际配置不符（模拟配置变更），但笔记文件真实存在。

**结果**：恢复判定「neither the file nor the row was written」并**提交该 intent**。

**后果**：笔记文件仍在磁盘上，但永久失去 DB 行 —— 用户看不到自己的笔记，且没有任何记录表明曾有写入意图。

**根因**：恢复盲信 intent 中记录的前缀。前缀过期时查找失败，而「查找失败」与「从未写入」被当成同一情况。

**修复**：
- 遍历所有合理前缀（记录的 / 配置推断的 / 空前缀）
- 找不到文件时不再提交 intent，改为 `no-evidence` 并保留

**验证**：四种情况（正确前缀 / 空前缀 / 错误前缀 / 文件确实不存在）—— 前三种重建行，第四种报告 `no-evidence`。

### 缺陷 2：零出站的声称范围大于证据

**攻击方式**：运行时观察真实网络请求。

**结果**：宿主页加载 3 个 CDN（jsdelivr / cdnjs / unpkg），共 8 个外部请求。

**问题**：ADR-009 第 151 行写「零 CDN 依赖」，措辞可被读成整个子系统无外部依赖。而论文工作台运行在宿主页内，会继承这些请求。

**修复**：措辞精确化为「论文子系统**自身**零 CDN 依赖」，并明确列出宿主页的既有 CDN。

**验证**：
- 静态：论文模块中外部 URL = 0
- 运行时：挂载论文工作台新增 10 个请求，外部请求 = **0**

## 四、测试工具的限制（无法验证的部分）

### 多标签页协调无法在此环境验证

**尝试**：开了两个真实标签页（t1、t2），在 t2 装监听器，从 t1 广播。

**结果**：t2 未收到。

**根因判定**（决定性证据）：
- t2 写入的 `localStorage` 在 t1 中读不到（`null`）
- 同一标签页内 BroadcastChannel 工作正常（自测得 1）

**结论**：两个标签页处于**不同浏览器上下文**（不同 profile/partition），因此 `BroadcastChannel` 与 `storage` 事件都无法跨越。这是**测试环境限制**，不是代码缺陷 —— 真实用户的两个标签页共享同一上下文，两种机制都会工作。

**诚实状态**：多标签页协调的**跨上下文行为未被验证**。已验证的是：
- 同一上下文内通道传递正常
- 自消息守卫生效（不回传）
- 降级路径存在（BroadcastChannel 不可用时回退到 storage）

3. **`source_positions` 的多设备语义**：明确为 `LOCAL_ONLY`，未做跨设备验证（符合 ADR-007 的范围声明）。

4. **P0.5/P1 范围**：高亮重绘、双向同步滚动、AI 接入均未实现，属计划内的后续阶段。

## 六、自审查的诚实结论

**能证明的**：
- 12 项声称中，10 项已升级为行为级证据
- 2 个真实缺陷被发现并修复（均经变异测试验证）
- 369 项测试通过，其中 34 个验收场景

**不能证明的**：
- 多标签页跨上下文协调（工具限制）
- 真实 Vault 规模下的完整流程（仅在副本验证）
- 是否还有未被我攻击到的地方 —— **没有独立审查者时，这类未知只能靠持续攻击缩小，无法消除**

**最重要的限制**：自审查无法替代独立审查。我攻击的是「我自己想到要攻击的地方」。Sol 的价值正在于它会攻击我没想到的地方 —— 例如上轮它用探针发现重命名会崩溃，那是我从未设想的方向。

在没有 Sol 的情况下，最接近的替代是：**先实际使用，让真实摩擦点充当审查者**。
